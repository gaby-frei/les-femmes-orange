Perspective Availability

What the Members page shows when a trust perspective cannot be served — and why none of it is styled as an error.

Slug pov-availability Date 2026-08-24 Surfaces toggle, indicator, search panel Reference ADR 0047 / pr-1

A refused perspective is a third perspective, not a failure

Nothing has gone wrong from the member's side. They asked to find someone on Nostr, and they will get ranked results. What changed is whose judgment ordered them.

The page already has a name for that idea and a place to show it. So the fallback gets named like the other two perspectives, in the same slot, in the same voice.

The page shows the most community-specific perspective that can actually be served: Les Femmes Orange first, the member's own second, unpersonalized last. The two are resolved independently, so a refusal of one says nothing about the other.

The fallback is not "the whole Nostr network." A refused personalized algorithm falls to the provider's default one, which is rooted in Brainstorm's own house account. What a member can actually verify is the negative — these results are not personalized to Les Femmes Orange — so that is what the copy claims, and nothing more.

The readiness check gates the toggle before a member can enter a hollow view. The provider's new refusal reaches exactly the same conclusion the old zero-score heuristic did.

The page moves the member to their own view

The two perspectives resolve independently, so a refusal of the community's ranking says nothing about the member's. When theirs works, showing it beats falling to a stranger's default account — the results stay personal to someone the member has a reason to trust.

Only the Community segment disables. My view is live and selected. There is nothing to switch back to, and the dimmed segment shows why.

This is the one place a perspective changes without the member asking, so it is the one place the change is announced. The indicator still reads searching as you — a substituted view and a chosen one produce identical results, and the why belongs in the status line.

Neither view can be served — the last resort

Only when both perspectives are refused does the page run unpersonalized. Every trust surface moves at once, so it says so in the place it always names the perspective.

Both segments go disabled. The toggle's proposition is a choice between two personalized perspectives. Here neither one is available, so offering the choice would misrepresent what the control does. Community keeps its white pill so the radio state stays readable — dimmed, not removed.

Grid cards keep their chips. They are real numbers, and the line above says what they are not.

The panel says what these rows are

The notice mirrors the shipped footnote inverted — that one sits below the rows with a rule above, this one sits above the rows with a rule below. Same family, opposite anchor, so the panel still reads as one designed object.

It claims only the negative. The app knows the community's ranking was refused; it does not know whose ranking replaced it, so it names none.

The notice belongs to this state alone. When a member is on their own substituted view the rows are personalized, and a caveat there would disparage the best results the page can produce.

It stays short because the indicator directly above already carries the reason. The panel says what these rows are; the toggle line says why. Neither repeats the other.

A refused perspective is never rendered as No profiles matched that search and never as Search is temporarily unavailable. Both would be false.

Either fall back to the endpoint's default algorithm 'graperank' for a global view, or provision this pov at https://brainstorm.nosfabrica.com — showing network-default results instead.

  • Emoji in product copy — banned by the language guardrail.
  • An em-dash sentence join — banned as a default connective.
  • Protocol vocabulary — pov, algorithm, graperank-pov, a 64-character hex key.
  • An operator's provisioning URL — an instruction a community member cannot act on.
  • The word "unavailable" in the results area — the results are right there.
  • "Network-default results" — inaccurate. The fallback is Brainstorm's default account, not the network at large.

The reason string is still captured. It goes to console.warn, where a developer can read it and a member cannot.

Six rules review will enforce

  1. A perspective is always named, and only one is named at a time. Every trust surface reflects the same perspective, and the active one is always on screen. No member should be able to read a number without being able to read whose view produced it.
  2. Protocol language never reaches a member. Reason strings, algorithm names, status codes, hex keys, and operator URLs are diagnostics. The app maps a machine state to its own plain sentence.
  3. Degrade to the best alternative that can be served. Prefer a personalized perspective over an unpersonalized one: community first, the member's own second, unpersonalized last. Claim only what the app can verify. It knows the community's ranking was refused, so it says results aren't personalized to the community. It does not know whose ranking replaced it, so it names none.
  4. Reserve error styling for errors. A perspective substitution is a status: small, grey, quiet, above the content it describes.
  5. A wait is described in the member's units. "Check back in about 10 minutes" is a designed state. "Still computing" is a shrug.
  6. Recovery is silent; substitution is not. Restoring a choice needs no words. Taking one does — when the page moves a member into a perspective they did not pick, it says so, once.
